## §0 已经测定的事实（五条，全部实测）

命令：`agenterm cli script run <file>`，引擎 `qjswasm`，上游 pin `21d8d9a`。

| # | 程序 | 位置 | 本引擎 | ECMA-262 | 判定 |
|---|------|------|--------|----------|------|
| 1 | `for (let i…)` 里造闭包 | 函数内 | `333` | `012` (13.7.4.7) | **错** |
| 2 | 同上 | 脚本层 | `333` | `012` | **错** |
| 3 | 循环体内 `let v = n` 被捕获 | 函数内 | `222` | `012` (14.3.1) | **错** |
| 4 | 同上 | 脚本层 | `222` | `012` | **错** |
| 5 | `while` 里造闭包 | 函数内 | `333` | `333` | **对**（`while` 无每轮环境） |

第 5 条是**对照组**，它说明这不是「闭包坏了」：捕获机制本身是对的，
错的是**一个绑定活多久**。

## §1 这条分歧其实是两条

事实 3/4 与事实 1/2 根因不同，必须分开修，否则只会修好一半还以为修完了。

### 半 A —— 声明再执行一次，应当是一个新绑定

`let v = n;` 写在循环体里，每轮都执行一次声明。ECMA-262 14.3.1：每次执行
创建一个**新的**绑定。本引擎把 cell 开在**函数入口**（`emit.rs::open_cells`），
整个函数一个，于是每轮写同一个格子。

这一条与 `for` 无关，`while`/`for`/嵌套块里都一样。**它是「声明」的语义，不是「循环」的语义。**

### 半 B —— `for` 头部的 `let` 每轮要复制一次

`for (let i = 0; …)` 的 `i` 只声明一次，所以半 A 修完它仍然是 `333`。
ECMA-262 13.7.4.7 的 `CreatePerIterationEnvironment` 是 `for` **专有**的规定：
每轮把循环变量复制进一个新环境，自增在新环境上进行。
这就是为什么事实 5 的 `while` 是对的——规范没给 `while` 这条。

**半 A 是「声明是什么」，半 B 是「`for` 额外承诺了什么」。** 先 A 后 B，
因为 B 的实现要站在 A 的机制上（复制到「一个新绑定」，得先有「新绑定」）。

## §2 存储模型：为什么脚本层不能照抄

函数里的捕获绑定是**堆 cell**（`open_cells`），修半 A 就是把分配从函数入口
挪到声明处。脚本层不是：`parse.rs:2316` 把任何脚本绑定解析成 `Res::Global`，
`emit.rs` §Storage 的理由是——

> A wasm local belongs to a frame. A nested function may read a script binding
> …so script storage has to outlive the script's frame -- which a local does not.

**这个理由成立，但它的结论今天已经过时了。** cell 正是「活过 frame 的一格存储」，
而写下这段话时闭包还没做（捕获闭包是 `68afb35`，晚于此）。今天有两种「活过 frame」
的办法，而这段话只知道一种。

所以本里程碑的第二步不是给脚本层加一套新机制，而是**减少一个特例**：

> **被嵌套函数读到的脚本绑定，改成 cell，按普通捕获处理。**
> 没有被任何嵌套函数读到的脚本绑定，仍然是 global。

收益是三重的：半 A 在两处用**同一份**代码修好；`Res::Global` 的适用范围缩小到
「真的没人捕获」；而**不用闭包的脚本一个 cell 都不分配**，零成本门自动成立。

### §2.1 判据 ④ 当场否掉了 §2 的第一版（2026-08-28，写代码之前）

上面那句「零成本门自动成立」**是错的**，而且是**事前判据抓住的，不是实测抓住的**——
这正是判据表要在开工前钉死的理由。

把「被嵌套函数读到的脚本绑定」全部改成 cell，会让这样一个程序变贵：

```js
let x = 1;                       // 脚本层，声明只执行一次
function f() { return x; }       // 嵌套函数读它
return f();
```

今天 `f` 读的是一个 global，**它根本不是捕获**，`captures` 是空的，所以这个程序
一分钱闭包的钱都没付。改完之后它变成真捕获：环境参数 + cell 前奏 + 创建点建环境，
按 `closures_m3.rs` 已经量到的数是 **+99 字节**。判据 ④ 写的是「含闭包但循环里
不捕获的程序，字节数不变，严格 0」——**直接违反**。

**修正后的 §2 规则**（这是本设计的最终形状）：

> 一个脚本绑定改成 cell，当且仅当它**被嵌套函数读到**
> **并且它的声明在一个循环体内**。

理由不是为了迁就判据，判据只是把它照出来了：14.3.1 的「每次执行创建一个新绑定」
**只在声明会执行第二次时才可观察**。只跑一次的声明，一个绑定和 N 个绑定给出的答案
完全相同，所以为它换存储是**纯成本，零收益**。

这条也解释了函数层与脚本层为什么处理得不对称，而那不是不一致：
函数层的捕获绑定**本来就是 cell**，把分配挪到声明处是免费的，所以不必区分在不在循环里；
脚本层要**换存储**，就必须只在真需要时换。**免费的可以一律做，收费的必须按需做。**

实现上因此需要在 `Binding` 上多一个 `in_loop`，由解析器在声明处记下——
它是解析期就知道的事实，不必等到 `record_captures`。

## §3 判据（事前钉死）

| # | 判据 | 性质 | 通过线 |
|---|------|------|--------|
| ① | 事实 1–4 全部变成 `012` | 布尔 | 四条都对，缺一不可 |
| ② | 事实 5（`while`）仍是 `333` | 布尔 | **不许顺手「修」对的东西** |
| ③ | 不含闭包的程序，字节数不变 | 布尔 | **严格 0**，基线取改动前那个提交 |
| ④ | 含闭包但循环里不捕获的程序，字节数不变 | 布尔 | 严格 0 |
| ⑤ | 每多一个「循环内被捕获的绑定」的边际字节 | 斜率 | 记录，不设上限 |
| ⑥ | 上游套件与下游三条验证命令 | 布尔 | 失败集合逐条不变 |

判据 ② 是这张表里最容易忘的一条：`while` 的 `333` 是**正确答案**，
把它一起「修」成 `012` 是引入一条新分歧，不是多修了一个 bug。

判据 ③④ 的量法与模板 / 箭头 / 方法三次相同：`.qjs` 编译成 `.wasm` 的**字节数**，
基线是**改动前那个提交**编出来的同一个 `.qjs`，不是 stash 之后的当前树。

## §4 判决树与时间盒

```
1. 先做半 A（声明处分配 cell），只在函数内。测事实 3。
   若事实 3 变 012 且判据 ③ 为 0 → 继续。
   若判据 ③ 不为 0 → 停，先解决门控，不许带着代价往下做。
2. 再做 §2（脚本绑定改 cell）。测事实 4，并复测 ③④。
3. 最后半 B（for 每轮复制）。测事实 1、2，并复测 ② 与 ③④。
kill criterion: 若 §2 迫使 `Res::Global` 完全消失（即所有脚本绑定都变 cell），
   说明这不是「减少特例」而是「换一套存储」，停下来重新立项——
   零成本门会挡住它，而那正是门存在的意义。
时间盒: 做到判据 ① 出结果为止。在此之前不做 for-of、不做 import、不做优化。
```

## §5 本里程碑不回答什么

- `break` / `continue`：`emit.rs` 记着本引擎没有它们。需求普查**没测这两个**，
  而 2026-08-29 之后普查表已经全绿，它们因此是最明显的下一个候选。
  **先数，再做**——`switch` 零使用就是这条规则的活证据。
- `for-in`：普查里 `for … of` 与 `for … in` 没分开数，`in` 的语义完全不同。
- 闭包捕获 `var`：`var` 是函数级、且从作用域进入就存在，本里程碑不动它的入口分配。
