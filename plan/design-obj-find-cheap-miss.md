# `__obj_find`：先看长度和两头的字，再问 `__str_eq`

| | |
|---|---|
| 日期 | 2026-08-31 |
| 状态 | 已落地：`runtime.rs` `obj_find`，`tests/obj_find_cost.rs` |
| 起因 | 下游 server-smoke 剖面（agenterm `plan/design-host-op-budget.md` §7）：`JSON.parse` 一个 20 键对象每成员 ≈2 500 步，其中 `__obj_set` 的线性键扫是大头 |

## 量

对象记录是线性表，`__obj_find` 从头走到答案，前面每一项都是一次未命中。此前每次未命中都进 `__str_eq`：
一次调用、比长度、再逐字节到第一个不同处——键同前缀时（`key000`…`key019`）**≈130 步一项**。
实测（进程内 `last_steps()` 差分）：20 键读最后一个 2 834、建 20 键字面量 27 623、100 键字面量 649 783、
`JSON.parse` 20 键对象每成员 2 533。

## 形状

不改记录布局。探针键只装载一次：长度、首字（长度不足四时按长度掩码——记录补到整字，但补的字节不承诺是什么）、
末字（长度 ≥ 4 时）。每一项：同一指针直接命中（字面量键对字面量存的键）；长度不同即未命中；首字不同即未命中；
末字不同即未命中（同一种写法造的键前缀相同、尾部不同——只比首字时 20 键反而更慢，31 143）；三关都过才 `__str_eq` 逐字节。
空键跳过字比较：`alloc(4)` 恰好四字节，其后的字可能在内存末尾之外。

指针相等是命中不是「同一记录才算」：`o[1]` 与 `o["1"]` 仍由 `__str_eq` 判成同一属性（`the_cheap_miss_never_confuses_two_keys`
钉了不足一字的键、空键、首尾同中间异、计算键、数字键对字符串键、覆盖写）。
