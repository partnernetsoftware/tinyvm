### 判决的适用范围，说清楚

C 赢在「**不向不相干的代码收费**」：它的成本全部落在真正写了方法调用的那几行上。
B 赢在「**方法调用点本身更便宜**」。两者的交叉取决于程序形状——
**方法调用点数 vs 函数值个数**。

以本仓真实脚本 `scripts/qjs/lib/fleet.qjs` 为参照（29 个函数），
B 光是 ③c 就要付约 870 字节，而 C 付 0；C 要输掉这 870 字节，
需要约 **40 个以上**的方法调用点。**对 agenterm 的脚本形状，C 明显更合适。**
若将来出现「函数极少、方法调用极多」的载荷，这条判决应当重开。

### 变体 A 的债，记下来即使它已出局

**本实验里的 A 并没有把 `this` 关键字加进语言**，只加了「调用约定携带接收者」
这个机制——方法需要的就是这个。把 `this` 暴露给脚本是**再往前一步**，
而那一步才会让 `plan/design-arrow-milestone.md` §1「箭头就是函数表达式」的等价作废。

**所以 A 的实测成本是个下界。** 它已经被 B 支配，把真正的 `this` 算进来只会更差。

### 三次「可修性检查」，每次都改变了结论

§2.6 那条规则在这条轨上救了三次，**其中一次直接改变了判决**：

1. **C 的判据 ③ 第一次读成 +307**（只调 `trim()` 的程序为 `indexOf` 买单）。
   原因是一刀切的门。改成逐方法门控 → **0**。
2. **B 的判据 ② 第一次多付 514 字节**（`return "ab".length;` 买了整套绑定设施）。
   原因是把臂挂在 `.length` 已打开的分支上。分开门 → **0**。
   第二次同样的病（surface 恒含 `map` 的体，拖进数组集合），按名字分别门控 → **0**。
3. **C 的 `map` 第一次读成每调用点 162 字节**，是 B 的 5.4 倍，
   眼看要按「线性且陡」判 C 负。原因是 C **内联了整个循环**——
   而它内联，只是因为当时以为「没有 prefab 能 `call_indirect`」。
   B 证明了能。给 C 也换成 prefab 之后：**162 → 48**，降到与它其它方法同一档。
   **判决因此从 B 翻到 C。**

第 3 条是这条轨最值钱的东西：**一个变体的数字，可能是被另一个变体的发现改变的。**
所以「可修性检查」不只是对自己那个变体做一次，而是**每当任何变体推翻一条共同前提时，
所有变体都要重测**。这一条已补进 `.claude/skills/decisive-experiment` §2.6。

## 判据 ⑥ 泄漏清单：变体 B（四条）

1. **B 打开闭包机制。** 绑定后的方法是个函数记录，而记录只有在程序有闭包时才带
   环境槽。所以一个**没有任何闭包**的程序，用了 B 的方法就要把整套闭包机制打开。
   C 不付这笔。
2. **B 需要函数表和统一签名。** 绑定方法是个函数值，所以程序哪怕自己一个函数值
   都没有，也要有表。C 不付这笔。
3. **B 有第二套环境布局。** 闭包的环境是 **cell** 的向量（绑定可以被写回）；
   绑定的接收者写不回（23.1.3 的方法不重绑 `this`），所以用了 12 字节裸对而不是
   cell——省一层间接，但引擎里多了一种形状。
4. **B 的门比 C 粗。** C 按**调用点**开门（`trim()` 被调用才开）；
   B 只能按**属性读**开门（读到 `trim` 这个名字就开），因为元素索引被烧进
   `obj_get`，而那是在谁也不知道源码里有没有 `trim` 之前发射的。
5. **B 要求 prefab 能 `call_indirect`**——把统一签名的 type index 交给 prefab 层。
   这是**入场费**，C 不付。（也正是它把泄漏 4 的前提推翻了一半。）
6. **B 抬高了统一签名的最小参数个数。** `map` 的 adapter 要转发一个 JS 值，
   所以哪怕程序里一个调用都没有，统一签名也得有一个值参数。**B 抬的是整张表
   共享的签名**，C 碰都不碰它。
7. **B 迫使类型段换个顺序生成。** prefab 是在统一签名被 intern **之前**建的，
   而 `__m_map_bound` 需要那个 index，所以 B 必须把统一签名提前——
   一个全局布局决定被一个变体改了方向。
8. **B 的跨门依赖比 C 广。** 读一个 `map` 就把**数组门**拉开（`__m_map_bound`
   要 `__arr_new`/`__arr_get`/`__arr_push`），这一条和 C 的 `push` 同类，
   但 C 的是「调用了才拉」，B 的是「读到名字就拉」。

**B 的一条结构性优势**：它的接收者测试**搭了顺风车**——`obj_get` 的 String 分支
本来就存在（`.length` 要它），B 的臂长在里面。C 的测试在调用点上，那里本来没有分支，
所以那 43 字节是**新开销**。这正是 B 斜率更低的原因。

## 分档：补测了，同时发现模板的三档对这个设计**不成立**（2026-08-28）

原记「L1/L2 未测定」。补测之后要说两件事。

### 一、L1 对「调用点特化」这个设计**不是一个单独的数**

skill §2.5.1 的三档假设机制是**一组函数**：L1 是纯机制码，L2 是机制加上跑通载荷
所需的全部代码。赢家的机制**不是函数**——它是发射在每个调用点上的类型测试与两个
`If`。所以 **L1 就是「每调用点」那个数**，没有第二个数可报。

这不是测不出来，是**这个设计没有那个东西**。照抄模板报一个 L1 只会是编造。

### 二、L2 分档（每个方法体，含它私有的 helper）

| 方法 | 方法体 | 每调用点 |
|---|---|---|
| `trim` | **518**（含 `ws_width`） | 83 |
| `indexOf` | **337**（含 `units`） | 94 |
| `push` | **73** | 101 |
| `pop` | **108** | 75 |
| `map` | **151** | 164 |

口径：每一对程序**只差一个调用点**，其余完全相同——同样的运算符、同样的操作数
个数、同样的字面量。`x.m() + x.m()` 对 `x.m()` 是**错的**比法，那样会把 `+` 和
多出来的那个表达式一起算进方法头上；改成 `x.m() + x` 对 `x.m() + x.m()` 才干净。

### 三、这里的「每调用点」与判据 ③b 的**不是同一个数**，别混

| | 基线 | 量的是 | 数值 |
|---|---|---|---|
| **判据 ③b** | 同源码、feature 关掉的构建 | 「调用已经写在那儿了，**加上这套机制**要多少」 | 43–53 |
| **本节** | 同构、**没有那个调用**的程序 | 「**写一个方法调用**总共要多少」 | 75–164 |

两个都对，答的是两个问题。③b 是为了**比较三个变体**——那时必须扣掉「任何机制都要
付的通用调用路径」，否则三边都背着同一笔账，比较被稀释。本节是产品视角：
**写一次 `.trim()` 一共花多少**。

判决用的是 ③b，而且判决当时三个变体是在同一把尺下比的，**结论不受本节影响**。
