## 度量条件

- **边界**：整个 `.wasm` 产物——机制码、方法体、数据段全在内。
- **工具**：`compile_qjs_m1(src).len()`，全轨一把尺，**不跨工具相除**。
- **构建**：guest wasm。`no_std` / `panic=abort` 那条轴在这里**不适用**，
  这些数**不得**与 host 侧二进制的字节并排。
- **目标/执行**：wasm32，且下表每个程序都被 `method_conformance.rs` **真跑过**，
  不是只量不跑的产物。
- **档位**：全部是 **L3**。**L1（纯机制）与 L2（机制+方法体）未测定**，
  拆开需要逐函数尺寸；下面任何一个数都不得被当成 L1 或 L2。
- **基线**：同一份源码、同一个提交，只切 `--features method-callsite`。

## 判据 ⑤（截距）与**每调用点**的斜率

| 程序 | off | on | Δ |
|---|---|---|---|
| 一个 `trim()` 调用点 | 9828 | 10563 | **735** |
| 两个 | 9887 | 10666 | **779** |
| 三个 | 9949 | 10770 | **821** |
| 一个 `indexOf()` 调用点 | 9841 | 10582 | **741** |
| 两个 | 9911 | 10700 | **789** |
| 一个 `trim()` + 一个 `indexOf()` | 10054 | 10838 | **784** |
| `o.trim()`（接收者是普通对象） | 9941 | 10677 | **736** |

**每多一个调用点：779−735 = 44，821−779 = 42，789−741 = 48。约 43–48 字节/调用点。**
方法不同也一样（`trim`+`indexOf` 两个点 = 784，与同方法两个点 779 相差在字面量里），
这说明**每调用点的代价是机制的，不是方法的**。

上表是**集合里有两个方法**时的读数。集合里只有 `trim` 时，前四行分别是
428 / 472 / 514 / 429——差额见下面判据 ③。

两个数**不要搞混**：同一构建里 trim1→trim2 是 +103，但其中 59 是那条新字符串
字面量本身的代价，off 构建也付。**43 是 Δ 之差**，减掉了字面量。
（这正是「不得跨口径相除」那条：+103 是「两个程序的差」，+43 是「机制的边际」。）

### 这个斜率是规格里没有的第四条

规格 §3 的 ③ 只写了「加**第五个方法**的边际字节」。变体 C 露出了另一条斜率：
**每多一个调用点**。它对 A、B 应当接近 0（分派在值里，不在调用点），
对 C 是 43。规格已按 §8「发现规格 bug 就修规格」补入这条判据。

## 判据 ③（主判据，加一个**方法**的边际）：**变体 C 目前是线性且陡**

实现第二个方法（`indexOf`，连同它要的 `units` 助手）之后，重测**同一个只调用
`trim()` 的程序**：

| 程序 | 集合里 1 个方法时 | 集合里 2 个方法时 | 变化 |
|---|---|---|---|
| `return "  a  ".trim();` | Δ **428** | Δ **735** | **+307** |
| `o.trim()`（普通对象） | Δ 429 | Δ 736 | +307 |

**一个只写了 `trim()` 的程序，为它永远不会调用的 `indexOf` 多付了 307 字节。**

原因是这一版的门是**整集合一刀切**：`scan.methods` 是一个 bool，开了就发射
`SET` 全部。所以每加一个方法，**所有用到任何方法的程序**都要再付一次。

按 §4 判决树第 1 条——「若某变体在任一条边际上是**线性且陡** → 判负，不看截距」
——变体 C 目前判负。

### 但先别落判决：这条是不是**可修**的

一刀切的门是**本实现**的选择，不是变体 C 的定义。可以改成**逐方法**门控：
`scan.methods` 变成「哪几个方法被调用」的集合，`SET` 的成员随之变化。

代价是**索引会移动**——正是 `plan/design-string-length-milestone.md` §3 里
`Rt::Len` 那个问题：位置决定偏移量的集合，抽掉一个成员，后面全挪。
要么把偏移量改成按启用子集计算，要么给每个方法一个固定槽位再留空洞。

**这笔改造本身的成本要算在变体 C 头上**，因为 A、B 不需要它：它们的方法是
函数值，只有被引用的那个才需要存在。

**所以 ③ 现在的读数是「307，且待定」**，不是「307，判负」。
下一步就是把逐方法门控做出来重测——在那之前，
**任何「C 因边际成本判负」的结论都是抢跑**。

## 判据 ⑥ 泄漏清单（变体 C，目前三条）

1. **运行期接收者测试省不掉。** 源码写 `x.trim()`，`x` 是 String 还是带 `trim`
   属性的对象要到运行时才知道，而
   `method_conformance::a_plain_object_property_named_like_a_method_is_untouched`
   就是「第二种必须照常работать」的断言。所以 C **省掉的是函数值，不是分派**——
   分支只是从被调用者的值里搬到了每一个调用点上。这也正是上面那 43 字节。
2. **接收者只能求值一次**，所以非 String 那条路**不能**退回去调现成的
   `indirect_call`——那会重新降级 callee，`f().trim()` 就会把 `f` 调两次。
   于是必须有暂存对 + 两个 `If` 的形状。
3. **IR 没有 `Else`，`BlockType` 只有 `Empty`**，所以「产生一个值的分支」必须
   经由一个局部变量绕一圈。这是 IR 的性质不是变体的，但**付钱的是变体**。

另外记两条**不是**泄漏、但会影响读数的事：

- `objtrim` 花了 429 字节却一次也到不了 prefab——**门是不精确的**，而且不可能精确，
  理由同泄漏 1。
- `ws_width` 只认 ECMA-262 12.2/12.3 里**具名的十个**，不认 `Zs` 的其余
  （U+1680、U+2000..200A、U+202F、U+205F、U+3000）。这是**已知缺口**，
  三个变体各付同样的字节，**不影响比较**；但方法体若被扶正就必须先补上。
