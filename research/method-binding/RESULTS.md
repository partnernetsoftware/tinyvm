## 判据 ⑤（截距）与**每调用点**的斜率

| 程序 | off | on | Δ |
|---|---|---|---|
下表是**逐方法门控之后**的读数（当前实现）：

| 程序 | off | on | Δ |
|---|---|---|---|
| 一个 `trim()` 调用点 | 9828 | 10256 | **428** |
| 两个 | 9887 | 10359 | **472** |
| 三个 | 9949 | 10463 | **514** |
| 一个 `indexOf()` 调用点 | 9841 | 10205 | **364** |
| 两个 | 9911 | 10323 | **412** |
| 一个 `trim()` + 一个 `indexOf()` | 10054 | 10838 | **784** |
| `o.trim()`（接收者是普通对象） | 9941 | 10370 | **429** |

**每多一个调用点：472−428 = 44，514−472 = 42，412−364 = 48。约 43–48 字节/调用点。**
`trim` 与 `indexOf` 各自的斜率一样，说明**每调用点的代价是机制的，不是方法的**。

两个数**不要搞混**：同一构建里 trim1→trim2 是 +103，但其中 59 是那条新字符串
字面量本身的代价，off 构建也付。**43 是 Δ 之差**，减掉了字面量。
（这正是「不得跨口径相除」那条：+103 是「两个程序的差」，+43 是「机制的边际」。）

### 这个斜率是规格里没有的第四条

规格 §3 的 ③ 只写了「加**第五个方法**的边际字节」。变体 C 露出了另一条斜率：
**每多一个调用点**。它对 A、B 应当接近 0（分派在值里，不在调用点），
对 C 是 43。规格已按 §8「发现规格 bug 就修规格」补入这条判据。

## 判据 ③（主判据，加一个**方法**的边际）：**先读成陡，做了逐方法门控后是 0**

**第一次读数（整集合一刀切的门）**：实现第二个方法 `indexOf` 之后，重测**同一个只
调用 `trim()` 的程序**：

| 程序 | 集合里 1 个方法 | 集合里 2 个方法（一刀切） | 变化 |
|---|---|---|---|
| `return "  a  ".trim();` | Δ **428** | Δ **735** | **+307** |

一个只写 `trim()` 的程序，为它永远不会调用的 `indexOf` 多付 307 字节。
按 §4 判决树第 1 条，这是「线性且陡」，本该判 C 负。

**但没有落判决，因为一刀切是本实现的选择、不是变体 C 的定义。**
做了**逐方法门控**（`method::Plan`：调用点要哪个就发哪个，helper 按依赖拉入）后重测：

| 程序 | 逐方法门控后的 Δ |
|---|---|
| 只用 `trim` | **428**（回到只有一个方法时的数） |
| 只用 `indexOf` | **364** |
| 两个都用 | **784** |

**加第五个方法，对不调用它的程序边际是 0。** 判据 ③ 因此**不判 C 负**。
（428 + 364 = 792，实测 784，8 字节的差在 LEB128 宽度与字面量上；
两个方法之间**没有**共享成本，符合「各付各的」。）

**这次修改本身的代价要算在 C 头上**：`method::Plan` 是 **27 行**（非空非注释），
而且它存在的理由是函数索引由**位置**决定——抽掉一个成员后面全挪，
正是 `plan/design-string-length-milestone.md` §3 里 `Rt::Len` 那个问题的第二次相遇。
**A、B 不需要这 27 行**：它们的方法是函数值，只有被引用的那个才需要存在。

**方法论上的一条**：第一次读数如果当场落判，就会用一个**可修的实现细节**
判掉一个变体。§4 判决树该在「这个数是变体的性质还是这次实现的性质」问清楚之后才走。
这条已写进本文件，也是这条轨迄今最值钱的一次教训。

## 判据 ⑥ 泄漏清单（变体 C，目前三条）

1. **运行期接收者测试省不掉。** 源码写 `x.trim()`，`x` 是 String 还是带 `trim`
   属性的对象要到运行时才知道，而
   `method_conformance::a_plain_object_property_named_like_a_method_is_untouched`
   就是「第二种必须照常работать」的断言。所以 C **省掉的是函数值，不是分派**——
   分支只是从被调用者的值里搬到了每一个调用点上。这也正是上面那 43 字节。
2. **接收者只能求值一次**，所以非 String 那条路**不能**退回去调现成的
   `indirect_call`——那会重新降级 callee，`f().trim()` 就会把 `f` 调两次。
   于是必须有暂存对 + 两个 `If` 的形状。
3. **IR 没有 `Else`，`BlockType` 只有 `Empty`**，所以「产生一个值的分支」必须
   经由一个局部变量绕一圈。这是 IR 的性质不是变体的，但**付钱的是变体**。

另外记两条**不是**泄漏、但会影响读数的事：

- `objtrim` 花了 429 字节却一次也到不了 prefab——**门是不精确的**，而且不可能精确，
  理由同泄漏 1。
- `ws_width` 只认 ECMA-262 12.2/12.3 里**具名的十个**，不认 `Zs` 的其余
  （U+1680、U+2000..200A、U+202F、U+205F、U+3000）。这是**已知缺口**，
  三个变体各付同样的字节，**不影响比较**；但方法体若被扶正就必须先补上。
